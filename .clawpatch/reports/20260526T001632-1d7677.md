## medium: Bookmark object_id cannot represent BigAutoField primary keys

id: fnd_sig-feat-library-253ded5d79-38fe_6656e2d852
category: data-loss
confidence: high
triage: confirmed-bug
status: open
feature: Python source learning_resources/migrations (feat_library_253ded5d79)

evidence:
- learning_resources/migrations/0001_initial.py:17-23
- learning_resources/migrations/0001_initial.py:46-52
- learning_resources/migrations/0005_recipe.py:16
- learning_resources/migrations/0007_bookmark.py:20-25

Article, Video, and Recipe all use BigAutoField primary keys, but Bookmark stores the generic target ID in a PositiveIntegerField. On databases such as PostgreSQL this is a 32-bit integer with a maximum of 2147483647, while BigAutoField is 64-bit. Once a learning resource row ID exceeds the 32-bit range, creating a bookmark for it will fail or be impossible, breaking the bookmark contract for valid target objects.

recommendation:
Change Bookmark.object_id to models.PositiveBigIntegerField, or to a CharField if bookmarks are intended to support arbitrary content types with non-integer primary keys. Add a migration that alters the column type without narrowing existing values.

test analysis:
No linked tests are included for migrations or bookmark behavior, and typical fixtures create small IDs that would not expose the 32-bit overflow boundary.

suggested regression test:
Add a migration/model test that creates or simulates a target object with an ID greater than 2147483647 and verifies a Bookmark can be saved for it.

minimum fix scope:
Alter learning_resources Bookmark.object_id to a 64-bit-compatible field and generate the corresponding migration.

- hub/migrations/0016_remove_fast_unique_name_church_fast_year_and_more.py:14-26

This migration removes the existing unique constraint on fast name/church, adds year as nullable, then replaces the constraint with uniqueness across name/church/year. On common Django-supported SQL backends, unique constraints do not treat NULL values as equal, so multiple Fast rows with the same name and church can coexist while year is NULL. That creates a data integrity hole compared with the removed unique_name_church constraint.

recommendation:
Backfill year for existing Fast rows before adding the new constraint and make the field non-null if uniqueness must always include year, or use a conditional/expression constraint that preserves uniqueness for NULL years.

test analysis:
No tests are included for this migration group, and migration tests would need to assert duplicate Fast rows with NULL year are rejected after 0016.

suggested regression test:
Add a migration test that migrates through 0016 and attempts to create two Fast records with identical name/church and NULL year, expecting an IntegrityError or an explicit non-null validation path.

minimum fix scope:
Update migration 0016 to backfill year and enforce non-null, or add an additional uniqueness constraint for rows where year is NULL.
