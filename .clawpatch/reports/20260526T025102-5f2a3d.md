## high: Authenticated users can read other users' event data

id: fnd_sig-feat-library-cad5f68928-2ceb_d844cef1be
category: security
confidence: high
triage: confirmed-bug
status: open
feature: Python source events (feat_library_cad5f68928)

evidence:
- events/views.py:23-100 (EventListView.get_queryset)
- events/views.py:103-114 (EventDetailView)
- events/serializers.py:33-56 (EventSerializer)

EventListView and EventDetailView require only IsAuthenticated and do not scope non-staff requests to request.user. The list endpoint also accepts an arbitrary user query parameter, and the detail endpoint has no object-level ownership check. Serialized event details include other users' usernames, emails, IP addresses, event data, target IDs, and activity metadata, so any logged-in user can enumerate or fetch other users' event records by ID.

recommendation:
Scope EventListView and EventDetailView to request.user for non-staff users, and only allow staff/admin users to query arbitrary users or retrieve arbitrary event objects. Consider removing user_email and ip_address from non-admin serializers.

test analysis:
Included tests cover authentication for engagement tracking and admin dashboard permissions, but they do not exercise event list/detail endpoints with two non-staff users or assert object-level access control.

suggested regression test:
Add API tests where user A creates an event and user B requests the list, filters by user A's id, and fetches user A's event detail; all should omit or deny user A's data unless user B is staff.

minimum fix scope:
events/views.py queryset scoping/object permission plus serializer exposure review for non-staff responses.

repro:
Authenticate as a regular user, request /events/events/?user=<another_user_id> or /events/events/<event_id>/ for another user's event, and observe the response instead of a 403 or user-scoped result.

triage: confirmed-bug
status: open

evidence:
- learning_resources/tasks.py:63-89
- learning_resources/tasks.py:121-133
- learning_resources/tasks.py:151

cleanup_orphaned_bookmarks_async captures the initial queryset count, pages through the live queryset by offset, and deletes orphaned bookmarks inside each batch. Deleting rows shrinks the queryset, so the next offset is applied to the remaining rows and can jump over records. For example, with 2,000 orphaned bookmarks and batch_size=1,000, the first batch deletes rows 0-999, then batch_start becomes 1,000 against a queryset that now only has the former rows 1000-1999, causing the loop to fetch an empty second batch and leave 1,000 orphaned bookmarks behind.

recommendation:
Iterate over stable primary-key windows or materialize the IDs to process before deleting. Alternatively, repeatedly process the first batch until no matching bookmarks remain, avoiding offset pagination on a mutating queryset.

test analysis:
The included tests exercise bookmark flags in detail views and general model behavior, but they do not cover the Celery orphan cleanup task with more than one batch or verify that all orphaned bookmarks are removed after batch deletion.

suggested regression test:
Create more orphaned Bookmark rows than the batch_size, run cleanup_orphaned_bookmarks_async with dry_run=False and a small batch_size, then assert every orphaned bookmark has been deleted and deleted_count matches the initial orphan count.

minimum fix scope:
Update cleanup_orphaned_bookmarks_async batching logic in learning_resources/tasks.py and add a focused task test for multi-batch deletion.
